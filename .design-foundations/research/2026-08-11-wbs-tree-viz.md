# CodeSearch — WBS 계층 트리/다이어그램 시각화

CodeSearch(K-water/조달청 BIM 코드·기준 검색 웹앱)에 WBS 계층 구조를 보여주는 시각적 다이어그램을 새로 추가한다.

**Date:** 2026-08-11
**Status:** confirmed

## Open questions
- 다이어그램의 정확한 인터랙션(클릭 시 검색 필터 연동 여부, 노드 확장/축소 방식 등)은 plan/mock 단계에서 결정.
- L5→L6 prefix-match로 못 걸린 5개 L6 코드(CEF/CEG/CEH/CEI/CEJ — 대응하는 L5 "CE"가 데이터에 없음)를 트리에서 어떻게 표시할지(미분류 묶음 등) 결정 필요.

## What
기존 CodeSearch에 없던 새로운 시각적 요소로 WBS 계층을 다이어그램화한다 — 단순 리스트/필터 나열을 넘어 "이 코드가 전체 구조에서 어디에 있는지"를 그림으로 보여주는 것이 목표. 그린필드 디자인이 아니라, 이미 배포되어 쓰이고 있는 기존 서비스의 다음 단계 발전.

## Why this scope (data-grounded constraint)
WBS 원본 데이터를 직접 검증한 결과:
- **L1→L2→L3 (시설 축)**: 완전한 진짜 계층 (9개 노드: L1 1개 + L2 2개 + L3 6개, 엣지 8개) — 이미 "적용 가능 경로" 기능에서 검증/활용 중.
- **L5→L6 (공종 축)**: L6 코드 442개 중 437개(98.9%)가 자기 L5 코드로 시작하는 패턴 확인 — 신뢰할 수 있는 진짜 부모-자식 관계.
- **L4 (시설 소분류, 71개)**: 코드 자체에 상위(L3) 식별자가 없어 데이터로 도출 불가.
- **L7 (공종 소분류)**: 원본 시트가 "상위 분류 불확실"로 이미 표시되어 있어 신뢰 가능한 부모 링크 없음.

사용자가 "전부 하나의 트리에 넣으면 경우의 수가 너무 많아 보기 힘들 것"이라는 우려를 제기했고, 이는 데이터 구조상으로도 맞는 지적 — WBS는 애초에 시설(L1-4)과 공종(L5-7)을 독립된 두 축으로 설계했으므로, 억지로 합친 단일 트리는 실제 구조를 왜곡한다.

**합의된 범위**: 두 개의 분리된 다이어그램
1. **공종 트리** — L5(대분류) → L6(중분류) 실제 부모-자식 가지치기. 리치한 시각화 (67→442 노드).
2. **시설 트리** — L1 → L2 → L3 실제 계층 (9개 노드, 작은 보조 다이어그램).
3. **L4/L7은 트리에 매달지 않음** — 리스트/태그 형태로 유지 (기존 "적용 가능 경로" 기능의 "직접입력" 철학과 일관).

## Who / context
실무 검색 도구 사용자(설계자 등) — 데스크톱 브라우저에서 사용, 정보 탐색/오리엔테이션 목적이지 마케팅적 임팩트가 목표가 아님. "예쁘게"보다 "구조가 실제로 이렇게 생겼구나"를 이해시키는 것이 성공 기준.
